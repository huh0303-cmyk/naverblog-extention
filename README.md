# naverblog-extention

네이버 블로그 자동화 by @복사장의생존발악

PC에 설치된 일반 Google Chrome에서 직접 로그인하고, Chrome 확장이 네이버 글쓰기 화면을 조작합니다. 앱은 글 생성, 계정 상태, 작업 기록을 관리합니다.

## 처음 연결하기

1. 앱에서 계정 표시명과 블로그 주소의 ID를 등록합니다. 네이버 로그인 ID와 블로그 ID가 다르면 **블로그 ID**를 입력합니다.
2. 해당 계정의 **블로그 열기 / 로그인**을 누릅니다. Windows는 일반 Chrome 바로가기를, macOS는 LaunchServices를 사용해 글쓰기 주소를 엽니다. 확장이 연결되면 로그인 상태도 확인합니다.
3. 로그인 화면이 나오면 사용자가 직접 로그인합니다. 비밀번호는 앱에 입력하지 않습니다.
4. 앱의 **크롬 확장 설치 → 설치 폴더 준비**를 누릅니다. 앱 데이터 폴더 아래 고정된 `chrome-extension` 폴더가 준비되고 경로가 복사됩니다.
5. **방금 연 계정 창** 주소창에서 `chrome://extensions`를 열고 **개발자 모드 → 압축해제된 확장 프로그램을 로드합니다**를 누른 뒤 준비한 폴더를 선택합니다.
6. 앱에서 계정의 **확장프로그램 연결**을 누르고, Chrome 확장 아이콘에서 **BlogAuto**를 열어 10자리 코드를 입력합니다. 코드는 한 번만 사용할 수 있고 10분 뒤 만료됩니다.
7. 최초 확장 연결 후 자동으로 대상 블로그의 글쓰기 권한을 확인합니다. **세션 일괄 확인**으로 계정별 창을 열고 연결 상태를 다시 확인할 수 있습니다. 로그인이 필요하면 앱은 완료될 때까지 대기합니다. 대기는 계정별로 취소할 수 있습니다.

‘로그인 미확인’은 로그아웃 판정이 아니라 아직 유효한 확인 결과가 없다는 뜻입니다. 계정명 클릭은 설정·카테고리 편집 계정을 선택하며, 체크박스는 자동 발행 및 세션일괄확인 대상을 선택합니다.

확장 개발자 모드와 폴더 선택은 Chrome이 사용자에게 요구하는 최초 수동 단계입니다. 앱이 설치 폴더 준비, 경로 복사, 계정 창 실행, 연결 코드 발급을 돕습니다. 웹 스토어 등록, 레지스트리 강제 설치, `--load-extension`은 사용하지 않습니다.

## 여러 네이버 계정

- 여기서 계정은 **네이버 블로그 계정**입니다. Google 계정 로그인이나 동기화와 연결하지 않습니다.
- 각 계정 창은 같은 정식 Chrome 실행 파일을 사용하지만 로그인 저장 폴더가 다릅니다. 같은 창에 탭만 추가해서 다른 계정을 관리하지 않습니다.
- 최초 로그인과 확장 설치는 계정 창마다 한 번 필요합니다. 이후 **블로그 열기**로 해당 계정의 창과 로그인을 재사용합니다. 창을 닫아도 로그인 저장 정보는 지우지 않습니다.
- 앱과 확장은 로그인 쿠키를 읽거나 서로 교체하지 않습니다. 로그인 저장은 Chrome이 담당합니다.
- 실행 인자는 계정의 `--user-data-dir`와 블로그 URL뿐입니다. Playwright, Selenium, CDP, 원격 디버깅, 자동화 전용 플래그, 확장 debugger 권한은 사용하지 않습니다.
- **연결 끊김**, **로그인 대기**, **세션 유효**, **추가 인증**, **계정 불일치**, **확인 불가**를 구분합니다. 창이 닫혔다고 로그인 만료로 판단하지 않습니다.
- 사이트가 다시 로그인을 요구하거나 추가 인증을 표시하면 사용자가 해당 Chrome에서 처리합니다. 확장 사용이 사이트의 접근 허용을 보장하는 것은 아닙니다.

## 글 생성과 검수

주제 선정·검색 판단 → 글 작성 → 최종 사실 검수 → 이미지 생성 순서입니다.

- 별도의 작성 계약 재작성 호출을 제거했습니다. 연구 단계에서 작성 지침을 함께 만듭니다.
- 전체 생성 시도는 최대 3회입니다. 성공하면 즉시 종료합니다. 자동 모드는 실패 원인을 반영해 다른 주제·범위를 탐색하고, 수동 모드는 입력 주제를 유지하며 검색 방법을 변경합니다. 세 번 모두 실패하면 설정된 반복 간격만큼 대기합니다.
- 각 시도 안의 검색 보강은 최대 두 번입니다. 이미 실행한 검색어와 실제 전달 발췌가 같은 재검토를 생략합니다. 새로운 검색 자료를 우선 반영하며 서로 다른 공고의 쿼리 ID를 보존합니다.
- 본문은 시도별 최초 작성 후 필요한 경우 한 번만 수정합니다. 모델 실행·사용량 오류는 즉시 중지하고, 이미지 실패는 이미 생성된 본문을 보존합니다.
- 정책 등 엄격한 근거가 필요한 검색은 웹 검색과 공식 원문·PDF/HWP/HWPX 첨부 탐색을 사용합니다. PDF는 텍스트를 추출하고 스캔·이미지 포함 페이지는 설치된 한국어·영어 Tesseract OCR로 로컬 판독합니다. HWP 본문·표는 HWPJS로, HWPX는 XML로 읽습니다. 별도 한컴 설치나 문서 외부 전송은 필요하지 않습니다.
- 문서는 최대 12MB, PDF는 80쪽·OCR은 20쪽까지 처리합니다. 문서 판독은 최대 2개 별도 프로세스에서 수행하며 각 180초 제한을 둡니다. 한도·OCR 신뢰도·미판독 영역은 근거에 함께 전달합니다. 암호화·배포용 HWP와 HWP/HWPX 삽입 이미지 내부 글자는 지원하지 않습니다. 추출 실패는 로그로 남기고 다른 근거를 찾습니다.
- `npm run test:documents`로 한국어 스캔 PDF 및 HWP/HWPX 샘플 판독을 확인할 수 있습니다. 최초 실행은 HWPJS 공개 샘플을 내려받고 이후 로컬 파일로 검사합니다. 결과는 `artifacts/document-validation.json`에 저장됩니다.
- `runtime/jobs/<작업ID>/attempts.json`에 회차별 사유·검색어·토큰을, `attempt-1` 등의 폴더에 단계별 프롬프트·결과·전달 근거를 보존합니다. `events.jsonl`은 진행 로그입니다. 작업 이력의 상세 보기에서도 시도별 사유와 토큰을 확인할 수 있습니다.
- 사실 검수는 원문 발췌와 핵심 주장·출처 ID 연결을 사용합니다. 도메인 목록, 검색 점수, 출처 개수만으로 통과·실패시키지 않습니다.
- 문체, 길이, 태그 부재, 모든 소제목에 이미지가 없다는 이유만으로 본문을 실패시키지 않습니다.
- 코어는 JSON 형식, 파일, 이미지 번호, 실행 횟수를 확인합니다. 문장·문맥·사실성 판단과 작성은 모델이 담당합니다. 날짜 문장을 정규식으로 삭제하지 않습니다.
- 이미지 실패 시 본문을 보존하고 자동 발행을 멈춥니다. 다른 Codex 작업의 최근 이미지를 추측해서 가져오지 않습니다.
- 사용량 배지를 갱신하기 위한 별도 모델 호출은 하지 않습니다. 최근 로컬 사용량 기록이 없으면 미확인으로 표시합니다.

제목 후보 3개의 독자 효익·근거 있는 훅·검색 의도를 Research의 기존 응답 안에서 비교합니다. 같은 제목은 Main 로그에 반복 표시하지 않습니다. Writer는 본문에 참고 번호를 넣지 않고 맨 아래 참고자료에 실제 출처 링크를 정리하며 Main이 제목의 약속·사실·출처 범위의 일치를 검수합니다. 허위 체험, 키워드 나열, 과장된 시급성, 근거 없는 내돈내산 표현을 금지하고, 전달받은 대가성 정보는 표시하도록 지시합니다. 경제적 관계를 앱이 자동으로 알아낼 수는 없으므로 해당 정보는 발행 목적 등에 명시해야 합니다.

검색·추천 품질 지침은 [네이버 D.I.A. 안내](https://help.naver.com/service/5626/contents/22926?osType=COMMONOS), [C-Rank 안내](https://help.naver.com/service/5626/contents/22927?osType=COMMONOS), [블로그 운영정책](https://notice.naver.com/api/v1/file/download/123)을 참고했습니다(2026-09-21 확인). 이는 노출·추천 보장이나 모든 정책의 자동 준수 인증이 아닙니다. 정책 변경은 별도로 검토해야 합니다.

## 작성과 발행

확장이 네이버 편집기의 제목, 본문, 인용구 버튼, 이미지 업로드, 발행 설정을 조작합니다. 기존 임시글은 덮어쓰지 않습니다. 내용·이미지 반영을 확인하지 못하면 발행 버튼을 누르지 않습니다. 네이버 DOM이나 편집기 동작이 바뀌면 확장 어댑터 수정이 필요할 수 있습니다.

발행 중 앱·확장이 중단되거나 결과 URL이 확인되지 않으면 **발행 결과 확인 필요**로 처리합니다. 같은 원고를 자동으로 재전송하지 않습니다. 특히 예약 발행은 결과 화면을 확인할 수 없는 경우 예약 목록에서 직접 확인해야 합니다.

네이버 계정 설정에 **티스토리 Blog ID**를 입력하면 해당 블로그로 이어 발행합니다. 비우면 네이버만 발행합니다. ID(예: boksajang) 또는 https://boksajang.tistory.com 주소를 입력할 수 있습니다. 티스토리는 하나의 로그인 계정과 공용 Chrome 창을 사용하고, 블로그마다 Chrome 창을 추가하지 않습니다. 공용 로그인 또는 세션 일괄 확인으로 공용 창을 열 수 있습니다.

공용 Chrome에도 BlogAuto 확장을 설치하고, 계정 목록 아래 **티스토리 공용 로그인 → 확장프로그램 연결**에서 코드를 발급받습니다. 블로그에 해당 카테고리와 쓰기 권한이 있는지 생성 전에 확인합니다. 네이버 성공 기록은 티스토리가 실패해도 보존하며, 다시 시작하면 완료된 네이버 발행을 건너뜁니다. 티스토리의 비공개 저장은 예약을 지원하지 않으므로 현재 비공개 저장 또는 공개 예약을 선택합니다.

네이버 입력은 실제 컴포넌트 ID와 입력된 원고 순서를 매 단계 확인합니다. 동일 원고의 완료된 부분은 재입력하지 않으며, 다른 글이나 부분 입력이 감지되면 기존 내용을 보존합니다. 화면 좌표 보정만으로 성공을 판단하지 않습니다. 사이트 편집기 구조 변경 시에는 어댑터 검증이 필요합니다.

## 화면

메뉴 없이 하나의 작업 화면을 사용합니다. 기본은 다크 모드이며 상단 버튼으로 라이트 모드로 전환합니다. 입력 영역은 왼쪽, 넓은 제목·본문 영역은 오른쪽입니다. Main·Research/Title·Writer 로그는 본문 위 작업 영역 최상단에 항상 표시하며, 같은 메시지의 연속 반복과 무제한 누적을 제한합니다.

## 실행·검사·빌드

Node.js 24 이상과 npm, 정식 Google Chrome, 로그인된 Codex CLI가 필요합니다. 모델 호출 권한과 이미지 생성 기능은 사용하는 Codex 환경에 따라 달라집니다.

```sh
npm ci
npm start
```

`npm start`는 개발모드로 실행하며, 계정·설정·확장 연결 데이터는 이 저장소의 `runtime` 폴더를 사용합니다. 기존 `npm run start:runtime`도 동일하게 동작합니다. 별도 요청이 있을 때만 배포용 빌드를 수행합니다.

```sh
npm run check
npm test
npm run test:ui
npm run test:editor
npm run dist
# macOS에서 빌드
npm run dist:mac
```

`test:ui`와 `test:editor`는 이 앱과 로컬 HTML만 검사하며 사용자 Chrome을 자동화하지 않습니다. `scripts/manual-login-test.js`는 `BLOGAUTO_TEST_BLOG_ID` 환경 변수로 지정한 블로그의 수동 로그인 연결만 도와줍니다. 이 스크립트는 글 생성이나 발행을 호출하지 않습니다.

기존 브라우저 자동화용 `run:saved`, `publish:latest`, CAPTCHA/Playwright E2E 스크립트는 제거했습니다. 앱의 작업 흐름을 사용합니다.

## 저장 경로와 업데이트

배포 앱은 운영체제의 앱 데이터 폴더를 사용합니다. 실행 파일이나 GitHub 소스 폴더를 옮겨도 해당 앱 데이터는 유지됩니다. **폴더 열기**로 실제 작업 데이터 경로를 확인할 수 있습니다.

- `runtime/account-categories.json`: 블로그·카테고리 설정
- `runtime/account-chrome/<계정 해시>`: Chrome이 관리하는 계정별 로그인 저장 공간
- `runtime/chrome-shortcuts`: Windows 계정 창 바로가기
- `runtime/extension-connections.json`: 로컬 확장 연결 키
- `runtime/extension-tasks.json`: 중단·중복 발행 방지용 작업 기록
- `runtime/jobs`, `runtime/image`: 생성 원고와 이미지
- 앱 데이터의 `chrome-extension`: 고정 확장 설치 폴더

기존 작업 폴더를 계속 사용하려면 `BLOGAUTO_RUNTIME_ROOT`에 그 폴더의 절대 경로를 설정합니다. 예전 자동화 브라우저 저장 폴더는 새 Chrome 폴더로 복사하지 않으므로 최초 로그인은 다시 필요합니다. 개발용 실행과 배포 앱의 기본 데이터 경로는 서로 다릅니다.

업데이트 후 **설치 폴더 준비**를 다시 누르고, 연결한 각 Chrome의 확장 관리 화면에서 **BlogAuto 새로고침(↻)**을 누릅니다. 기존 설치 폴더를 삭제하거나 이동하지 마세요.

GitHub에는 소스만 배포합니다. `runtime`, `account-chrome`, 연결 키, 작업 기록, 개인 이미지, `.env`는 커밋하지 않습니다. `.gitignore`에 제외했습니다. macOS 실행·실제 네이버 발행은 Windows의 로컬 테스트만으로 검증된 것으로 간주하지 않습니다.

변경 이유와 검증 범위는 [전환 점검 기록](docs/migration-audit.md)을 참고하세요.

### 블로그 휴머나이저

본문 생성 → 블로그 휴머나이저 → Main 검증 → 이미지 생성 순서로 처리합니다. 작성된 본문은 윤문 시작 때부터 화면에 표시됩니다. 휴머나이저는 이미 자연스러운 문장을 유지하고, 제목·섹션·이미지 위치·참고자료를 바꾸지 않습니다. Main은 최종 원고와 수정 전후를 함께 확인합니다. 윤문 오류가 발생하면 원본을 보존하고 주제 재탐색을 중지합니다.

Main은 변경 문단마다 유지 또는 원문 복원을 결정합니다. 복원할 문단만 정확히 되돌린 뒤 승인 원고와 이미지 단계에 반영하며, 코어에서 문장 의미나 특정 주제를 판정하지 않습니다. 검수 반려 후에는 피드백을 윤문에 전달하고 이전 반려 캐시를 재사용하지 않습니다.

독립 모듈과 Codex 스킬은 [packages/blog-humanizer](packages/blog-humanizer/README.md)에 있습니다. 다른 앱에서도 폴더 전체를 사용하고 모델 호출 함수만 연결하면 됩니다. 원본 프로젝트의 통계·점수표·보고서 생성은 포함하지 않습니다. 동일 작업 안의 같은 원고는 캐시를 재사용하며, 발행·티스토리 재시도에서는 이미 완성된 원고를 사용합니다.

`node scripts/test-humanizer-live.js`는 저장된 테스트 원고로 **실제 Codex 호출 비용이 발생하는** 비교 테스트입니다. 결과는 `runtime/humanizer-tests`에 저장하며 이미지 생성·발행은 하지 않습니다. 일반 `npm test`에는 이 유료 테스트가 포함되지 않습니다.

### 검색과 공식 원문 검증

- 카테고리의 주제 탐색 탭(블로그/뉴스/웹)은 탐색 검색에 적용합니다. 블로그 탐색 결과는 블로그 글만 수집합니다. Google 대체 검색도 블로그 설정을 따릅니다.
- Research가 필요한 핵심 근거를 지정한 경우 `verificationQueries`로 별도 공식 원문 웹 검증을 수행합니다(회차당 최대 2개). 블로그에 출처 링크가 없어도 무조건 제외하지 않습니다. 도메인이나 자료 개수만으로 신뢰 여부를 확정하지 않습니다.
- 같은 작업의 검색 결과와 판독 원문을 공유합니다. 같은 원문은 다시 다운로드하지 않고 필요한 발췌 구간을 다시 선택합니다. 기본 작업 한도는 검색 요청 24회, 원문 60개, 첨부 8개입니다. PDF 자동 수집은 앞 40쪽, OCR 최대 4쪽이며 미판독 범위는 에이전트에 알립니다. 이 제한은 문서 전체가 검증되었다는 뜻이 아닙니다.
- 공식 페이지에서는 해당 문서의 첨부를 우선 수집하고 관련 사업 메뉴를 재귀적으로 탐색하지 않습니다. 링크 추적은 최대 2단계입니다.
- 새 원문 근거가 없으면 에이전트 재검토와 나머지 전체 시도를 중단하고 이유를 기록합니다. `runtime/jobs/<작업>/retrieval-audit.json`에서 실제 탐색 채널·검색어·원문 오류·요청 수를 확인할 수 있습니다.
- 법률 검증 지침은 법령·시행령·시행규칙·조례·행정규칙·판례·해설을 구분합니다. 적용 시점, 시행일, 부칙·경과조치, 판결의 사건번호·선고일·사실관계를 대조하며, 오래된 자료라는 이유만으로 배제하지 않습니다. 국가법령정보센터 법령 프레임은 식별자와 적용일을 유지한 채 조문 본문으로 읽습니다. 사이트별 동적 화면·접근 제한 또는 이미지 판독 한계는 여전히 있을 수 있습니다.

### 조사 및 검수 비용 제어

첫 조사에서는 잠정 주제와 검색어만 만들고, 확보한 자료로 설명 가능한 범위를 정한 뒤 제목과 작성 계획을 확정합니다. 첫 검색은 탐색 2개·공식 검증 1개, 추가 보강은 합계 2개로 제한합니다. 자동 주제는 유용한 범위로 좁힐 수 있지만 수동 주제는 유지합니다.

기본 전달 자료는 8개이며, 인용한 자료가 더 많으면 최대 16개까지 우선 보존합니다. 자료당 발췌 한도는 3,000자입니다. 토큰 통계와 중복 요약은 다음 에이전트에 전달하지 않습니다. 최종 검수는 실제 본문의 근거 이탈·조건 누락·출처 오류를 확인하며, 부가 정보나 형식만으로 재조사를 요구하지 않습니다. 실제 생성 시간과 토큰 감소량은 실행별 로그로 확인해야 합니다.

## 공통 근거 처리

분야별 코어 판정 대신 에이전트가 필요한 근거와 원문 위치를 지정하고, 앱은 발췌·캐시·중복 제거를 담당합니다. [공통 근거 처리 계약](docs/common-evidence-contract.md)을 참고하세요.

기존 [blogauto-naver](https://github.com/boksajang/blogauto-naver)를 바탕으로 Chrome 확장 방식으로 변경한 저장소입니다. 블로그 휴머나이저 원본 출처와 라이선스는 [NOTICE](packages/blog-humanizer/NOTICE.md)에 보존되어 있습니다.
